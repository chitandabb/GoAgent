# 005. Unified Agent Runtime Access and Stable Tool Profiles

## Status

Accepted as the target architecture on 2026-08-14 and completed as the hard-cut slice: the legacy authorization system is permanently deleted, not emulated. `TaskScope`, `ToolCapability`, `TaskTypeKnowledge`, `RequestedSkill`, the `request_scope` columns, `InvestigationPolicyMode`/`mode` and the compatibility adapters (`WithTaskScope`, `ToolsFor(TaskScope)`, `taskCapabilitiesFromScope`, `requestedSkillFromScope`) no longer exist in the runtime, API, database schema or frontend contract. Migration `00035` performs the hard cut (fail-fast on any NULL-Policy legacy task, never silently deleting rows) and is irreversible: its Down raises an explicit exception and restores nothing.

The current authorization model has exactly four facts:

- `ToolProfile` decides the model-visible Tool Schema, stable within one process-start/deployment Epoch. `ToolCatalog.ResolveProfile(profileID)` is the only production entry; both Runners resolve fixed Profile IDs (`conversation-default`, `diagnosis-default`; evaluations use the separate `evaluation-wide-v2` contract). Blocked/run-limit state, message references, `RunAccess` and transient dependency health never delete Schema.
- `RunAccess` decides, per run, whether a visible Tool may execute (`Permission`) and which concrete resources it may touch (`ResourceGrant`). The execution-time Permission/ResourceGrant Guard is fail-closed: unauthorized calls make zero underlying calls. `bounded_lab` safety mode never enters a data-source Grant.
- `InvestigationPolicy` is the task-level authorization frozen at Diagnosis task creation (migration `00033`; Policy JSON Schema v1, `investigation_policy_schema_version=1` is the current Policy JSON protocol version, independent of Runtime architecture version v2). The Worker derives `RunAccess` as frozen Policy ∩ current access ceiling; the legacy `mode` concept (`00034`) and `request_scope` are deleted by `00035`, and the Worker Task Policy is a non-pointer value — missing/corrupt/version-mismatch Policy is `ErrInvalidTask`.
- `Skill` carries diagnosis SOP only (entry fixed to `ticket-diagnosis`, read on demand via `skill/read_skill_reference`). It neither declares nor grants Tools and takes no part in authorization or Schema selection. No intent-classifier service and no Skill-to-Tool authorization binding exist.

Evaluation identity follows the generic v3 contract: `EvaluationObservation` records `observationSchemaVersion` (`evaluation-observation-v3`), `toolProfileId`, `toolSchemaFingerprint`, `modelProfileFingerprint`, `implementationRevision` and `implementationDirty`. The baseline arm must record `evaluation-wide-v2`, the experiment arm `diagnosis-default`; Tool Profile ID and Schema fingerprint are arm-specific contracts and are deliberately not required to be equal across arms, while the same variant across samples must keep one Profile ID and Schema fingerprint (fail-closed otherwise). The comparison itself is a whole-group contract fixed across all samples and both arms: `comparisonFingerprint`, `sharedToolNames` and `baselineOnlyToolNames` record the wide/production Tool comparison, and each v3 observation must also satisfy the AllowedTools set contract — the experiment arm's `allowedTools` set must equal `sharedToolNames`, the baseline arm's must equal `sharedToolNames ∪ baselineOnlyToolNames` (order-independent; duplicates, missing or extra Tools are fail-closed before any pairing). Paired reduction requires `model`/`modelVersion`/`reasoningEffort`/`promptVersion`/`modelProfileFingerprint`/`implementationRevision` to match and both arms `implementationDirty=false`. The active evaluator keeps no v1/v2 compatibility branch: historical v1/v2 assets may only be marked historical and never enter formal reduction.

## Decision

MESGuard keeps two execution modes, Conversation and Diagnosis, while treating SQL, knowledge, code, attachment, case and Web access as shared Tools rather than separate task types. The model decides which read-only Tool to call and in what order; application code owns authorization, resource ownership, QueryGuard, budgets, retries, degradation, evidence validation and state-changing command guards. No independent intent-classifier service and no Skill-to-Tool authorization binding are introduced.

`Capability`, `TaskScope`, `TaskTypeKnowledge`, `RequestedSkill` and dependency-health-driven Schema filtering are hard-cut deleted from the target vocabulary and from the codebase. A deployment-level `ToolProfile` determines the stable model-visible Tool Schema. A run-level `RunAccess` determines whether a visible Tool may execute and which resources it may touch. The Catalog keeps the guarded-wrapper seam: profile resolution selects Schema, the wrapper reads `RunAccess` from `context.Context` and checks coarse `Permission`, and the Tool implementation checks concrete `ResourceGrant` values before the existing infrastructure safety controls run. The SQL Tools resolve data sources from `RunAccess.Grants`, and `bounded_lab` never reaches the read-only SQL Tools. The Conversation case/task/attachment/create Tools also validate the concrete `ResourceGrant` values before the existing `CommandContext`/owner checks (which remain a second layer).

Diagnosis task creation freezes an `InvestigationPolicy`. Every Diagnosis run derives `RunAccess` from the intersection of that policy and the current emergency-revocation/resource-disable ceiling. Therefore:

```text
RunAccess.Permissions is a subset of InvestigationPolicy.Permissions
RunAccess.ResourceGrants are subsets of InvestigationPolicy.ResourceGrants
```

Conversation has no persisted Investigation Policy. Each turn derives `RunAccess` from the authenticated actor, conversation ownership and current structured references. Neither the model, a Skill, Tool arguments nor a later deployment configuration may expand an old Diagnosis task.

The Conversation Profile includes direct knowledge retrieval and safe Text-to-SQL Tools plus the guarded `create_diagnosis_task` command: successfully constructed `search_schema_catalog` and `execute_readonly_query` join the Conversation Profile, while `get_database_object_definition` remains Diagnosis-only under the minimal Tool-set principle (Text-to-SQL needs the published catalog and row execution, not object DDL). The Diagnosis Profile reuses read-only evidence Tools and the diagnosis SOP Skill but never exposes task creation. Skill remains a diagnosis SOP only; it neither declares nor grants Tools.

`ToolProfile` is a startup assembly snapshot frozen within one process-start/deployment Epoch: the Profile content is decided by which Adapters complete construction successfully at startup. After the Runtime starts, message references, `RunAccess`, call counts and transient dependency execution failures never delete Tool Schema; temporary dependency failure returns a structured unavailable/degraded result. If the service restarts and an Adapter cannot complete construction, that is a new startup Profile/Epoch, which must produce a new Tool Schema fingerprint, and its evaluation data must not be mixed with data from the old Profile. This document deliberately avoids the absolute claim that "only a configuration change can change the Profile": the guarantee is scoped to one startup Epoch.

Detailed implementation of this decision lives in [`design/agent-orchestration.md`](../design/agent-orchestration.md); the execution-time Permission Guard, the runtime-generic ResourceGrant Guard, Conversation `turn_context`, Diagnosis `InvestigationPolicy` persistence with `task_context`, and the hard-cut removal of the legacy authorization system (including the OpenAPI/frontend contract sync) are all wired.

Conversation `turn_context` is wired since this slice and its safe-projection contract is documented in [`design/agent-orchestration.md`](../design/agent-orchestration.md); Diagnosis `task_context` has landed as well: it contains only `policySchemaVersion`, effective permissions, the current case ID and the authorized data sources' id/role/safetyMode, is rendered with `encoding/json` (HTML-escaped), appended only at the tail of the Diagnosis system instruction, and counted identically by the context preflight. Current evidence gaps and attachments remain in user input. Existing canonical Tool Schema fingerprints and Prompt Epoch identity are reused. Evaluation records bind the v3 identity contract: `observationSchemaVersion` (`evaluation-observation-v3`), `toolProfileId`, `toolSchemaFingerprint`, `modelProfileFingerprint`, `implementationRevision` and `implementationDirty`; baseline must record `evaluation-wide-v2` and experiment `diagnosis-default`; the same variant across samples must keep one Profile ID and Schema fingerprint (fail-closed otherwise); paired arms must match `model`/`modelVersion`/`reasoningEffort`/`promptVersion`/`modelProfileFingerprint`/`implementationRevision` with both arms clean (`implementationDirty=false`). Tool Profile ID and Schema fingerprint are arm-specific contracts and are never required to be equal across arms, while the comparison contract (`comparisonFingerprint`/`sharedToolNames`/`baselineOnlyToolNames`) and the AllowedTools set contract (experiment = `sharedToolNames`; baseline = `sharedToolNames ∪ baselineOnlyToolNames`) apply to every v3 observation. The Generic paired comparison is a single-variable design: both arms use the same production SystemInstruction, the same ticket-diagnosis entry Skill full text, the same non-empty `task_context` generated once per case by the production `BuildDiagnosisRunContext` deep module (frozen Policy derived from the fixed case and its tags; ceiling from the real production `diagnosis-default` Profile tool names; SQL cases carry legal dataSourceId/role and read_only SafetyMode; non-SQL cases never attach data-source grants), the same model Profile and budget, and the only allowed difference is the final Tool Profile/Schema (`evaluation-wide-v2` for baseline, `diagnosis-default` for experiment).

## Consequences

- Main chat can perform direct knowledge Q&A and safe Text-to-SQL without first creating a Diagnosis task.
- Mixed questions remain Agentic and may use several read-only Tools in one turn without a single-label router.
- Tool Schema remains stable within one deployment, improving Prompt Cache comparability, while execution remains fail-closed per user and resource.
- The model Factory enforces a **Schema-isolation seam** at the Adapter boundary: `internal/platform/chatmodel` wraps every returned `model.ToolCallingChatModel` in a decorator that deep-clones `[]*schema.ToolInfo` (via `schema.ToolInfo`'s own MarshalJSON/UnmarshalJSON, preserving both the params and jsonschema representations) before `WithTools` and before call-time `model.WithTools(...)` options in `Generate`/`Stream`, and re-wraps bound models. This prevents third-party adapters (the Eino OpenAI ACL) from mutating shared ToolInfo/JSONSchema held by `InferTool.Info()` — the in-place `sort.Strings(jsonSchema.Required)` that drifted ToolProfile startup fingerprints, evaluation preflight fingerprints and runtime fingerprints (observed on clean `f5831a4`'s `ticket-read-01` probe; the production arm failed closed before its Provider request). The isolation layer also verifies that the model-visible JSON roundtrip is semantically faithful: equivalent numeric encodings may normalize, while missing fields or changed numeric values fail closed **before** the Adapter is called (e.g. `jsonschema.Schema.Extras` is `json:"-"`, marshaled by hand and dropped on unmarshal), never silently handing a changed Schema to the model. The decorator forwards Eino's callback-ownership and component-type contracts so instrumentation is not duplicated. Catalog, Skill middleware, Runner and the runtime/preflight hash checks are unchanged.
- The legacy `TaskTypeKnowledge`, `ToolCapability`, `TaskScope`, `RequestedSkill`, `request_scope` and `investigation_policy_mode` concepts are deleted, together with their compatibility adapters; migration `00035` is irreversible, so rollback requires a database restored from a backup taken before `00033`.
- Existing Tool internals, QueryGuard, Evidence Gate, Worker state machines, RAG and context governance are preserved; this decision changes their orchestration contract, not their safety implementations.
