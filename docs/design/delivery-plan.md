# MESGuard 交付计划

## 文档状态

- 本文把已经确认的产品、领域和系统架构拆成可执行的交付顺序。
- 当前仓库已完成 M0 与 M1-A1 后端；M1-A2 至 M4 仍是目标计划，不代表对应能力已经实现。
- 每个里程碑都以可验证的纵向闭环为完成标准，不以“目录已经创建”或“页面能够点击”为完成标准。
- 本文不定义具体 PostgreSQL 字段、RabbitMQ 拓扑、HTTP 字段或 Eino Graph 节点；这些内容在专项设计文档中单独确定。

## 交付原则

### 先闭环，再扩展

每个阶段优先交付一条能够真实运行、留痕和失败恢复的业务链路。数据库、队列、AI、前端不会并行铺设大量空壳接口。

### 先保证事实，再优化体验

任务、步骤、工具调用、证据、报告和事件先落 PostgreSQL，再通过 Redis 或 SSE 提升实时体验。缓存、消息队列和浏览器连接都不能成为唯一事实来源。

### 风险能力默认受限

SQL Server 只读、代码仓库只读、文件读取按权限和范围限制。模型输出必须经过结构化解析、权限校验和业务状态校验，不能直接执行高风险动作。

### 目标架构与当前实现分开

每个阶段的验收记录都必须标注：已实现、已验证、已知限制和后续计划。文档不能把计划中的 Eino、RabbitMQ、MinIO 或 React 描述成当前能力。

## 当前基线

当前已经具备 Web 基础、认证与 M1-A1 后端：

- Go 模块和 `cmd/internal` 项目布局；
- TOML 配置与不提交 Git 的 `.env` 覆盖；
- `bootstrap` 手动依赖装配；
- Gin 路由和基础健康检查；
- 统一成功/错误响应、错误码和全局错误处理；
- 请求 ID、Panic Recovery、404/405处理；
- Zap 结构化日志与 HTTP、PostgreSQL、Redis 的优雅关闭。
- Argon2id 本地账号、PostgreSQL Session、CSRF 与 analyst/admin 身份；
- 公司 ERP SQL Server 专用只读账号、统一工单映射、数据源发现、工单列表/详情与来源指纹；
- PostgreSQL 数据源/外部工单身份登记，以及默认单测和显式真实数据库集成测试。

当前明确没有实现：

- 登录、角色权限和业务 DTO 校验约定；
- PostgreSQL 业务迁移、领域表和事务规范；
- SQL Server 只读适配器与工单快照；
- RabbitMQ、Outbox、Diagnosis Worker 和 SSE 任务流；
- Eino 诊断编排、模型接入和受控工具；
- MinIO 附件、React 工作台和知识库入库。

## 总体顺序

~~~text
M0 基础约定与可测试启动
  ↓
M1 工单诊断闭环
  ├─ M1-A 数据源与工单快照
  ├─ M1-B 任务、事件与可靠投递
  ├─ M1-C Worker、SSE与取消
  ├─ M1-D 受控证据采集与Eino诊断
  └─ M1-E 报告、反馈与工作台
  ↓
M2 知识助手、RAG与混合文档入库
  ↓
M3 受限代码调查Agent
  ↓
M4 SQL性能实验室
~~~

M2必须建立在M1的用户、权限、附件元数据、TaskEvent、模型调用记录和可观测性基础上。M3和M4都不能反过来成为M1的前置条件。

## M0：基础约定与可测试启动

M0不是新的业务模块，而是让后续业务代码有稳定边界。

### 工作内容

1. 固化请求 DTO、参数校验、错误码和统一响应的使用约定。
2. 确定 PostgreSQL 迁移命令、迁移目录和启动时是否自动迁移。
3. 确定事务边界、事务中禁止执行的外部调用，以及仓储接口的返回错误约定。
4. 增加配置解析、必填项、启动失败和依赖未就绪测试。
5. 增加本地开发账号的最小认证骨架和角色枚举；不提前接入企业 SSO。
6. 把结构化日志字段约定写入开发文档，并让测试可以注入固定 logger 和 clock。

### 完成标准

- 新增业务模块不需要直接操作 Gin 响应或读取全局配置；
- 缺少关键配置时进程明确失败并输出脱敏原因；
- 数据库迁移可重复执行，失败时不会留下“半成功”状态；
- 至少有一组 API、配置和启动失败测试作为后续基线。

## M1：工单诊断闭环

M1是简历和产品演示的核心版本：用户从 SQL Server 工单开始，得到一份可追溯、可反馈、可恢复的诊断报告。报告是辅助判断，不回写 MES/ERP。

### M1-A：数据源与工单快照

工作内容：

- 建立只读 SQL Server 适配器和独立连接池；
- 建立数据源元信息、表/字段白名单、查询超时、行数和结果大小限制；
- 查询工单列表和详情；
- 发起诊断时在 PostgreSQL 保存不可变 CaseSnapshot；
- 建立 MinIO 私有对象存储和 Attachment 元数据，支持诊断图片上传、权限校验和任务引用；
- 消息和任务只保存 `attachment_id`，不保存永久 URL、Base64 或对象存储凭证；
- 保存实际使用的数据源、读取时间、内容哈希、脱敏和截断信息；
- 通过合成 SQL Server 数据验证不回写。

完成标准：同一个外部工单可以产生多个独立快照；外部工单后续变化不会改变历史诊断输入；附件保持私有且不能越权读取；越权表、超时查询和超大结果会被拒绝并留痕。

### M1-B：任务、事件与可靠投递

工作内容：

- 建立 DiagnosisTask、DiagnosisStep、ToolExecution、EvidenceItem、DiagnosisReport、ReportReview 和 TaskEvent 的最小持久化模型；
- 使用 PostgreSQL 事务同时创建快照、任务、首个事件和 OutboxEvent；
- Outbox Relay 发布 RabbitMQ 诊断消息；
- 设计消息重复投递、确认、有限重试和死信记录；
- 使用幂等键和数据库状态保护重复创建、重复消费和重复报告。

完成标准：事务提交成功后即使 API 在发布消息前崩溃，任务仍可由 Outbox 补发；消息重复投递不会生成两份业务报告；RabbitMQ 短时不可用时任务事实仍保留在 PostgreSQL。

### M1-C：Worker、SSE与取消

工作内容：

- 增加独立 Diagnosis Worker 启动入口和手动依赖装配；
- 原子领取任务，按步骤追加 TaskEvent；
- 提供任务查询和 SSE 事件读取；
- 使用事件序号支持断线重连和历史补读；
- 关闭浏览器只断开 SSE，不取消任务；
- 通过独立 HTTP 命令写入 `cancel_requested`，Worker 在步骤边界和工具调用边界检查取消；
- 对超时、临时依赖故障和不可恢复错误使用有限重试和明确失败状态。

完成标准：页面关闭后任务继续；重新进入可以补读完整事件；取消后不再执行后续步骤但已完成记录保留；Redis不可用时 SSE 可退化为 PostgreSQL 轮询。

### M1-D：受控证据采集与 Eino 诊断

工作内容：

- 接入实际选定的 ChatModel 和多模态模型，保留模型版本、Token、耗时和成本记录；
- 用 Eino 组件和编排能力装配诊断流程，不重复定义模型接口；
- 先实现预定义工具：工单快照读取、受控 SQL 查询、附件摘要读取和案例检索；
- 对 Text-to-SQL 实施 Schema Catalog、只读校验、字段脱敏、行数/时间限制和人工可审计记录；
- 采用结构化报告输出，严格解析并校验结论、证据引用和风险等级；
- 证据不足时生成 `inconclusive`，不强行猜测根因。

完成标准：每个报告结论都能定位到 EvidenceItem；模型不能绕过工具权限；SQL Server 永远没有写操作；模型失败、解析失败和证据不足不会被伪装成成功结论。

### M1-E：报告、反馈与最小工作台

工作内容：

- 提供业务摘要层和技术证据层报告；
- 提供 `adopted`、`partially_adopted`、`rejected` 反馈；
- 记录反馈说明和操作者，不改变外部 MES/ERP 状态；
- 将现有前端替换为能完成“选择工单→发起诊断→查看进度→查看报告→提交反馈”的最小 React 工作台；
- 使用 Nginx 作为生产入口，开发阶段允许 Vite 代理；
- 增加合成故障集和一条可重复演示脚本。

### M1 总验收

M1必须同时满足：

1. analyst 可以从真实或合成 SQL Server 工单创建诊断任务。
2. API 快速返回任务标识，完整诊断在 Worker 中运行。
3. 页面刷新、断开和 API 重启后，任务与事件仍可恢复。
4. 重复消息、重复请求和步骤重试不会产生重复业务结果。
5. 所有外部数据库访问只读且可审计。
6. 报告包含证据引用、结论可信度和明确限制。
7. admin 可以查看依赖状态、任务失败和积压情况。
8. 合成故障集可重复运行并输出耗时、Token、成本和诊断效果指标。

## M2：知识助手、RAG与混合文档入库

M2扩展“工单诊断”之外的知识问答，但不把自由聊天内容自动当作诊断证据。

### 主要交付

- 全局知识库和个人知识库；
- 会话临时文件，仅本次使用或保存到个人知识库；
- MinIO 原文件、PostgreSQL 元数据和权限关联；
- `read_attachment` 受控工具，按需读取文本、页码、行范围或多模态内容；
- 文本、表格、截图、图表和示意图的混合文档解析；
- OCR、表格结构恢复、VLM 结构化描述和原图关联；
- 百炼 `text-embedding-v4` 与重排模型的接入验证；
- pgvector 混合检索、重排、引用和来源展示；
- SSE 流式知识助手；
- 内部知识不足时可选的脱敏 Web Search；
- 检索质量、引用正确性、答案相关性和成本评测。

ONNX 图像分类器作为降低 VLM 调用量的增强路由。M2先用规则路由打通端到端流程，ONNX 原生运行时稳定后再纳入默认路径，避免它阻塞知识库基本能力。

### M2 验收重点

- 用户不能读取其他用户的个人知识库或私有附件；
- 原文件不直接永久塞入消息上下文；
- 检索结果保留来源、页码/位置和 attachment_id；
- VLM、OCR 或 Embedding 暂时失败时，文档状态明确为处理中/失败，不伪装成可检索成功；
- RAG 评测集可以比较不同切块、召回、重排和 Prompt 版本的效果。

## M3：受限代码调查 Agent

M3只支持一个已配置的私有代码库和指定版本，不做任意代码执行。

### 主要交付

- admin 手动同步仓库并固定 Commit；
- 只读 `rg` 搜索和 Git 文件/版本读取工具；
- 工具参数限制路径、关键词、返回行数和执行时间；
- 报告引用仓库、Commit、文件路径和行号；
- 将代码证据与工单、数据库和知识库证据统一进入 EvidenceItem；
- 对工具调用、权限拒绝和超时完整留痕。

### M3 验收重点

- 模型不能执行 Shell、写文件、切换到未授权仓库或读取仓库外路径；
- 同一 Commit 的调查可以复现；
- 代码缺失或版本不匹配时报告明确显示限制，而不是给出无来源结论。

## M4：SQL 性能实验室

M4是高风险能力，必须与生产数据库隔离。

### 主要交付

- 读取存储过程定义、执行计划和历史指标；
- 模型生成候选优化 SQL 或索引建议；
- 在隔离测试库建立可回滚实验；
- 执行前后 `EXPLAIN`/性能指标和结果集一致性对比；
- 生成优化报告、风险分级和适用条件；
- 高风险修改只输出建议，不自动执行。

### M4 验收重点

- 生产 SQL Server 永远不执行模型生成的写入、DDL 或替换操作；
- 性能提升不能以结果不一致为代价；
- 每次实验都有数据集、版本、执行计划、耗时和结论记录；
- 测试环境不可用时，系统只提供静态建议并明确未验证。

## 依赖与并行边界

| 工作 | 必须先完成 | 可以并行 |
| --- | --- | --- |
| M0 | 当前 Web 基础骨架 | 文档模板、合成数据准备 |
| M1-A | M0、SQL Server与MinIO连接配置 | React页面原型、报告样例 |
| M1-B | M0、PostgreSQL迁移规范 | SQL Server只读查询样例 |
| M1-C | M1-B | 前端任务状态页面 |
| M1-D | M1-A、M1-B、M1-C的任务与事件接口 | 模型POC、工具安全测试 |
| M1-E | M1-C、M1-D | 评测集和指标脚本 |
| M2 | M1的认证、附件元数据、模型记录和日志 | Embedding/Rerank POC |
| M3 | M1证据模型、M2附件/知识权限 | 代码库同步和搜索安全测试 |
| M4 | M1审计与权限边界 | 测试库数据集和执行计划采集 |

可以并行的是验证和准备工作，不是绕过依赖提前把业务能力接入生产路径。

## 推荐实现顺序

在开始大规模业务编码时，按以下纵向切片推进，每完成一片就运行测试和手动演示：

1. DTO 校验、迁移命令、事务封装和认证骨架。
2. SQL Server 只读连接、工单列表/详情、来源指纹与附件元数据。
3. MinIO附件固化后，将CaseSnapshot、DiagnosisTask、TaskEvent和Outbox放入同一事务创建。
4. Outbox Relay、RabbitMQ 消费和幂等 Worker；先用假诊断处理器验证可靠性。
5. SSE 历史补读、断线恢复、取消和重试。
6. 受控 SQL 工具、证据记录和结构化报告；再接入实际 Eino Graph。
7. 报告反馈、管理员状态页和合成故障评测。
8. React 工作台和 Nginx Compose 集成。
9. 在M1稳定后再进入个人知识库、混合文档解析和知识库文档入库；M1已经具备诊断附件的MinIO基础能力。

## 每个阶段的交付证据

每个里程碑完成时至少保留以下证据：

- 变更说明和架构决策记录；
- 可重复执行的迁移、启动和测试命令；
- API 或 Worker 的成功、失败、超时、重试和恢复样例；
- 关键日志、TaskEvent、指标和脱敏后的报告样例；
- 依赖故障或重复消息测试记录；
- 当前已实现能力与剩余限制清单；
- 如果涉及模型，记录模型版本、Token、成本和评测集版本。

## 暂不做的扩展

在M1稳定前不做：

- Kubernetes、跨主机高可用和自动弹性扩容；
- 企业 SSO/OIDC；
- 多租户隔离；
- 用户上传内容自动公开或审核状态机；
- 任意 Shell、代码执行或生产 SQL 写入；
- 复杂的多 Agent 自主协商；
- 以 Prometheus/Grafana 平台建设替代基础业务埋点。

这些能力不是永久禁止，而是当前会扩大故障面和验证范围，暂不作为主链路前置条件。
