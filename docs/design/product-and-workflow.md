# MESGuard 产品定位与业务流程

## 文档状态

- 本文描述 MESGuard 的目标产品边界和业务流程。
- 当前仓库已实现只读 ERP 工单浏览后端；完整诊断闭环、知识问答和实验能力仍未实现。
- 本文只回答“系统为谁解决什么问题，以及用户如何使用”，不展开数据库表、接口字段和 Eino Graph 节点。

## 产品定位

MESGuard 是面向工业软件公司的售后、实施、运维和产品支持人员的诊断辅助系统。

它从现有 MES/ERP 工单出发，结合用户补充的图片、聊天截图和问题描述，受控地采集数据库、知识库以及必要的代码证据，生成一份可以追溯和人工判断的诊断报告。

MESGuard 的目标不是替代开发人员，而是先完成重复的信息收集、证据整理和常见问题定位，减少非开发人员与开发人员之间来回确认问题、补充日志和解释业务数据的沟通成本。

## 产品目标

1. 让非开发人员能够从已有工单直接发起诊断，不需要掌握 SQL 或代码。
2. 将工单描述、附件、数据库结果、知识案例和代码片段组织成可审核的证据链。
3. 对常见问题给出通俗、可操作的处理建议。
4. 对复杂问题生成结构化的技术材料，帮助开发人员更快接手。
5. 在证据不足时明确拒绝猜测，并说明仍缺少哪些信息。
6. 通过报告反馈和已验证案例沉淀，持续量化并改善诊断效果。

## 明确不做的事情

MESGuard 不是现有 MES/ERP 的替代系统，也不是生产数据库管理工具。

系统遵守以下边界：

- 不向现有 MES/ERP 回写工单、报告或业务状态。
- 不自动执行 `UPDATE`、`DELETE`、DDL、Shell 脚本或代码发布。
- 不允许模型不受限制地查询生产数据库或读取整个代码仓库。
- 不把模型生成的结论直接当作业务事实。
- 不展示模型原始内部思维、系统 Prompt 或不适合普通用户查看的原始 SQL；只展示应用生成的结构化、脱敏调查轨迹。
- 不因为任务执行成功就宣称诊断结论正确。

业务人员根据报告自行判断，并回到原 MES/ERP 完成工单填写和后续业务操作。

## 用户角色

一期只设置两个角色。

### analyst

面向售后、实施、运维和产品支持人员，可以：

- 查询有权限查看的外部工单；
- 发起、取消和重新发起诊断；
- 查看诊断进度、证据和报告；
- 对报告提交采纳、部分采纳或驳回反馈；
- 使用知识助手，并按需使用公开网络搜索。

### admin

拥有 analyst 的全部能力，并额外负责：

- 管理用户和角色；
- 管理数据源元信息与只读连接配置；
- 审核 Schema Catalog、知识文档和案例卡片；
- 管理模型、全局知识内容和系统级配置，并查看代码源集成状态；
- 查看系统运行、索引和评测状态。

一期使用本地账号和基于角色的访问控制，架构上为以后接入企业 SSO/OIDC 保留边界。

## 统一工作台与两个业务模式

MESGuard 使用一个统一 Agent 聊天工作台承载知识问答、工单讨论和诊断任务命令。会话本身不固定为“知识会话”或“诊断会话”，也不绑定一个主工单或诊断任务；后端知识回答和异步诊断仍使用不同的执行、持久化和预算边界。

~~~text
左侧：知识/诊断会话历史
中间：统一聊天、Agent 进度与报告
右侧：当前卷宗（主工单、附件、数据源、待办工单）
~~~

- 右侧卷宗是当前用户可选择的工单和附件上下文，不是会话所有权；
- 选择工单本身不调用模型、不创建任务，发送消息时才把所选工单固化为结构化消息引用；
- 用户明确要求诊断时，会话 Agent 调用受控的 `create_diagnosis_task` Tool；模糊表达先澄清；
- 一个会话可以创建或引用多个工单的多个任务，任务也可以通过深链接或其他会话查看；
- 会话与任务的关联只用于来源追溯和导航，关闭或归档会话不取消、不删除任务；
- 新附件或后续要求通过新的 follow-up 任务形成新快照，不修改历史任务和报告；
- 一个任务固定自己的 CaseSnapshot、附件版本和实际证据范围，历史运行不被后续变化覆盖。

会话中的单条消息或文件可以显式引用到一次任务命令，但系统不能自动把整段会话复制进诊断上下文。稳定边界见 [`../decisions/004-conversation-driven-diagnosis-commands.md`](../decisions/004-conversation-driven-diagnosis-commands.md)。

### 工单诊断

工单诊断是核心业务。它使用固定、可审计的诊断流程，以异步任务方式运行，产出证据链和诊断报告。

它强调：

- 任务能够在用户关闭页面后继续运行；
- 每一步工具调用都可以追溯；
- 诊断结论必须引用证据；
- 同一工单可以多次诊断，历史结果不被覆盖；
- 数据库、知识库、代码和公开网络工具都受到权限约束。

### 知识助手

知识助手用于解释术语、产品功能、常见问题和具有时效性的公开信息，以流式对话方式工作。

它强调：

- 企业知识库优先；
- 内部知识不足或问题具有明显时效性时，才使用公开 Web Search；
- 联网查询前必须移除工单号、客户名称、日志原文和数据库内容等内部信息；
- 联网回答必须提供来源链接和检索时间；
- 用户可以关闭联网能力；
- 用户停止生成后保留已有回答，并标记为“生成已中止”。

知识助手的自由回答不会自动成为工单诊断证据。需要进入报告的内容必须经过诊断流程重新采集和引用。

聊天上下文采用按需读取附件的策略。上下文组装器只放入附件标识、文件名、类型、大小、处理状态和可用读取方式，不预先注入所有图片、PDF或日志内容。模型明确判断某个附件与问题相关时，才调用受控的 `read_attachment` 工具读取有限内容。

`read_attachment` 根据附件标识执行权限校验，从 MinIO 读取原始对象或解析结果，再以有限文本或多模态工具结果返回给模型。模型不能直接传入 bucket、object key、文件系统路径或对象存储凭证。

这样可以避免用户上传多个大文件后把完整内容一次性塞进 Prompt，也保留模型在后续推理阶段重新查看指定附件的能力。

知识内容分为三个范围：

```text
全局知识库
    由管理员通过受控导入维护，组织内按权限共享

个人知识库
    当前用户自己保存和管理，其他用户默认不可见

本次会话文件
    只在当前会话或当前诊断任务中使用，默认不长期保存
```

用户上传文件时只提供两种选择：`仅本次使用` 或 `保存到个人知识库`。一期不实现“申请加入全局知识库”、公开审核或个人资料发布状态机。这样可以保护默认隐私，也避免把个人上传流程扩展成内容治理系统。

全局知识库仍然存在，但它是管理员维护的系统内容边界，不是用户上传后自动晋升的结果。未来如果确实需要案例共享，再单独设计脱敏、审核和版本流程。

## 外部工单与数据归属

现有 MES/ERP 运行在 SQL Server 中，并继续作为工单和业务数据的事实来源。

一期采用“按需快照”方式：

1. 工单列表和详情实时读取 SQL Server。
2. 用户发起诊断时，将当时的工单内容保存为 MESGuard 工单快照。
3. 后续诊断基于该快照执行，避免外部工单变化后无法解释历史报告。
4. 同一外部工单再次诊断时创建新的快照和任务，不覆盖旧记录。

系统按多数据源设计，能够区分工单库、生产业务库和产品参考库。一期只启用当前已有的一个数据源，暂不建设复杂的数据源管理后台。

发起诊断时，系统根据工单中的客户、产品、工厂和环境信息推荐证据数据源，由用户确认或修正。实际使用的数据源集合随任务保存。

## 工单诊断主流程

```text
登录 MESGuard
    ↓
查询并选择 SQL Server 中的工单
    ↓
查看只读工单信息
    ↓
在统一工作台右侧卷宗选择该工单
    ↓
输入诊断目标并按需附加文件
    ↓
会话 Agent 读取工单并判断是否调用创建任务 Tool
    ↓
受控 Tool 创建工单快照和异步任务
    ↓
查看实时步骤和证据采集进度
    ↓
查看两层诊断报告
    ↓
人工标记：已采纳 / 部分采纳 / 已驳回
    ↓
业务人员回到原 MES/ERP 处理并填写工单
```

用户发起诊断时可以输入类似“引发这个问题的原因是什么，请先检查数据库”的自然语言要求，但系统不会因此绕过工具权限和诊断流程。

## 诊断执行原则

诊断任务采用持久化异步执行。任务创建后立即返回任务标识，页面通过 SSE 接收进度。用户刷新或关闭页面不会终止任务。

用户可以主动取消任务。取消请求会停止后续步骤，已经完成的步骤、工具调用和证据仍然保留用于审计，但不生成正式报告。

同一工单重新诊断时始终创建新任务。即使用户点击“重试”，也通过关联关系指向原任务，不在原记录上覆盖执行历史。

任务执行状态与报告结论状态相互独立：

```text
任务执行状态：pending / running / cancel_requested / succeeded / failed / cancelled
报告结论状态：conclusive / probable / inconclusive
```

`succeeded` 只表示系统正常完成诊断并生成报告。证据不足时，任务仍可正常完成，但报告必须标记为 `inconclusive`。

## 证据来源

诊断可以按需使用以下证据：

- 发起诊断时保存的工单快照；
- 用户上传的问题图片、聊天截图和其他附件；
- SQL Server 中经过白名单、限时和限量控制的查询结果；
- 正式产品资料和经过人工确认的历史案例卡片；
- 与指定代码版本对应的有限代码片段；
- 经过脱敏的公开网络搜索结果。

数据库证据只保存经过字段白名单、脱敏和截断处理的快照，不复制整张业务表。代码调查只允许使用受控、只读的搜索和版本查看工具。

任何证据都必须保留来源、采集时间和必要的版本信息。无法确认来源或版本时，报告必须显示限制条件。

附件不会因为出现在消息记录中就自动进入模型上下文。消息只保存 `attachment_id` 和轻量元数据；具体内容通过 `read_attachment` 按需读取，并把本次读取的附件、页码或行范围记录为证据引用。

## 诊断报告

报告采用两层结构。

### 业务摘要层

首先向非技术人员说明：

- 问题概述；
- 最可能原因；
- 影响范围；
- 建议如何处理；
- 是否需要联系开发人员；
- 当前结论及可信程度。

### 技术证据层

按需展开：

- 工单和附件摘要；
- 数据库证据；
- 相似历史案例；
- 产品文档引用；
- 候选代码片段及版本；
- 工具执行记录；
- 未确认信息、反例和限制条件。

处理建议按权限和风险分级：

- L1：业务人员可以在正常业务界面执行的操作；
- L2：管理员可以执行的系统维护操作；
- L3：需要开发人员分析、修改和发布的内容。

模型可以说明可能的数据、查询或代码问题，但不会向普通用户提供可直接执行的高风险命令。

## 报告反馈与案例沉淀

报告反馈不是审批流。使用人查看报告后，可以标记：

```text
待确认 → 已采纳 / 部分采纳 / 已驳回
```

反馈用于评估诊断效果，不会触发 MES/ERP 状态变化。

正式产品资料和人工确认过的历史解决方案可以由管理员整理进入全局知识库。AI 生成的报告不能自动回流；只有经过人工确认和脱敏整理后，才能转化为管理员维护的标准案例卡片。个人知识库中的文件不会因为被检索或被采纳而自动公开。

案例卡片至少包含问题现象、产品版本、环境、关键证据、已确认根因、解决方法、验证方式和不适用条件。

## 分阶段交付

### M1：证据化工单诊断闭环

- 本地账号与 analyst/admin 权限；
- SQL Server 工单查询和按需快照；
- 补充说明及图片附件；
- 持久异步任务、进度、取消和重试；
- 预定义数据库工具与受控 Text-to-SQL；
- 单 Agent Skill 编排与受限 GitHub MCP 代码调查；
- 诊断报告和人工反馈；
- 可重复运行的合成故障评测集。

### M2：知识助手与 RAG

- 全局知识库和个人知识库入库；
- 会话临时文件检索；
- 混合文档元素解析：文本、表格、截图、图表和示意图分流；
- OCR、表格结构化提取和多模态模型描述；
- 原始图片与混合检索块的 MinIO 元数据关联；
- 混合检索、向量检索和重排；
- 流式知识问答；
- 公开 Web Search 兜底；
- RAG 评测和引用质量评估。

M2 的图片处理先以规则路由、OCR、表格解析和 VLM 描述打通闭环。轻量 ONNX 分类器作为降低 VLM 调用量的增强路由，不作为整个知识库上线的前置条件。

### M4：SQL 性能实验室

- 读取存储过程定义、执行计划和历史指标；
- 由模型生成候选优化版本；
- 只在隔离测试库执行候选版本；
- 校验结果一致性并生成性能对比报告；
- 高风险修改只给出分级建议，不自动执行。

## M1 完成标准

M1 不是“页面能够点击”就算完成。它至少需要证明：

1. 用户可以从真实 SQL Server 工单创建一次可追溯的诊断任务。
2. 页面断开后任务继续运行，重新进入后可以恢复查看进度。
3. 重复消息不会导致同一任务重复产生业务结果。
4. 用户可以取消任务，已有执行记录不会丢失。
5. 所有数据库访问保持只读，并受到表、字段、行数和超时限制。
6. 报告中的结论能够定位到具体证据；证据不足时明确拒绝判断。
7. 报告反馈能够用于离线评测，但不会回写外部系统。
8. 版本化合成故障集可以重复运行并比较诊断效果、耗时、Token 和成本。
